# 多模型 Wiki 工作台：设计规格

**日期：** 2026-07-30
**状态：** 设计已确认，等待实施计划

## 1. 目标

构建一款本地、单用户的桌面应用。用户可以选择多个大语言模型，让它们在同一会话中自然群聊。每个模型都有角色，会独立决定是否回应每条新消息，并公开一条简短的“回应/保持沉默”理由。

应用同时维护一个长期知识库。文件、图片和网页快照是不可变的原始资料；对话结论与资料综合会被编译为 Markdown Wiki，并维护索引、时间日志和待复核队列。

首个版本交付完整闭环的薄切片，不做企业协作平台，也不做完整 RAG 系统。

## 2. 首版范围

- 面向单人的本地桌面应用。
- 支持用户自带 OpenAI、Anthropic、Google Gemini 和 DeepSeek 的 API Key。
- 每个会话可选择一个或多个模型，并为每个模型设置角色预设及可编辑角色指令。
- 用户发言后，模型可自然接话，且能自主选择回复或沉默。
- 显示模型状态：思考中、准备回复、已回复、保持沉默，以及简短公开理由。
- 支持 PDF、Word、Markdown、纯文本、常见图片和网页链接。
- 在本地保存原始资料和网页快照，并在群聊中作为带来源标记的共享上下文。
- 自动生成和更新本地 Markdown Wiki、`index.md` 与追加式 `log.md`。
- Wiki 更新立即生效，同时进入待复核队列，支持查看、接受、标记错误和回退。
- 支持原始资料元数据与 Wiki 页面的本地关键词、索引搜索。

## 3. 首版不做

- 多用户、团队空间、云端同步、共享额度、平台计费。
- 平台托管模型密钥或用量余额。
- 扫描件 OCR、批量爬取、定时导入、向量搜索、知识图谱可视化。
- 展示或保存模型原始内部推理。
- 纯浏览器直接调用模型；凭据、文件和模型请求必须留在桌面应用宿主中。

## 4. 架构

### 4.1 技术选型

- **桌面壳：** Tauri。
- **界面：** React 与 TypeScript。
- **本地服务：** 通过 Tauri 暴露的 Rust 命令。
- **运行数据：** SQLite。
- **知识库：** 人可阅读的 Markdown 文件。
- **密钥：** 操作系统凭据库，只允许桌面宿主访问。

Tauri 提供 Web 工作台体验，同时把凭据、文件访问和供应商调用隔离在渲染界面之外。

### 4.2 核心组件

| 组件 | 职责 |
| --- | --- |
| 群聊工作台 | 展示消息流、模型成员、资料、决策状态、控制操作和待复核状态。 |
| 模型适配层 | 归一化 OpenAI、Anthropic、Gemini、DeepSeek 的请求和响应。 |
| 讨论调度器 | 判断可发言模型、执行发言决策、排列回复、限制轮次并记录事件。 |
| 资料导入服务 | 复制文件、抓取网页正文、提取受支持文本并建立资料元数据。 |
| Wiki 维护器 | 在导入或讨论结束后生成带引用的 Markdown 更新和修订记录。 |
| 待复核队列 | 允许用户查看、接受、标记错误或回退自动写入的 Wiki 修订。 |
| 本地仓库服务 | 管理工作区目录、SQLite、关键词搜索以及资料与 Wiki 页的关联。 |

### 4.3 本地工作区结构

```text
workspace/
  raw/                 不可变的原始文件和网页快照
  wiki/                自动维护的 Markdown 知识库
    index.md           按内容组织的页面目录
    log.md             按时间追加的操作日志
    sources/           每份资料对应的摘要页
    topics/            概念与主题综合页
    entities/          需要时创建的实体页
    conversations/     群聊结论页
  data/
    workbench.sqlite   会话、消息、元数据、修订和任务状态
```

API Key 不会出现在以上目录或应用日志中。

## 5. 核心流程

### 5.1 配置模型

1. 用户选择供应商并输入 API Key。
2. 桌面宿主将密钥保存至操作系统凭据库，并发起轻量校验请求。
3. 界面显示可用、密钥无效、服务不可用或额度受限状态。
4. 一个会话成员由供应商模型标识、角色预设和可选的编辑后角色指令构成。

首批角色预设为：分析师、质疑者、创意者、事实核查者。角色只影响参与视角，不覆盖用户明确提出的任务。

### 5.2 自然群聊

1. 用户消息、模型消息或“继续讨论”操作创建一次调度事件。
2. 除发言者外的所有可参与模型，收到当前可见对话与相关资料的带引用上下文。
3. 每个模型返回结构化决策：`reply` 或 `silent`、简短公开理由和优先级。
4. 选择回复的模型进入事件队列，按优先级排序；优先级相同则使用稳定顺序。
5. 调度器依次调用队列中的模型；每一条模型回复都会创建下一次调度事件。
6. 当所有可参与模型选择沉默，或本轮累计产生 12 条模型消息时，本轮结束。

用户可随时停止、继续讨论或点名某个模型。同一模型默认不能连续发言；除非被明确点名，发言后必须等待其他模型发言才可再次参与。

界面只显示简短公开理由，不请求、不展示、不保存，也不尝试推断私有链式推理。

### 5.3 资料和上下文

1. 用户将资料附加到当前会话，或导入到工作区。
2. 宿主将文件复制至 `raw/`，或把网页正文与元数据保存为不可变快照。
3. 提取可支持的文本并建立索引；在适合时，将图片交给具备视觉能力的已选模型。
4. 对话上下文携带资料标识、标题和有限摘录；基于资料的模型表述保留来源引用。
5. 提取失败时保留原始资料并显示失败原因，不生成不可靠的替代摘要。

首批支持带嵌入文本的 PDF、DOCX、Markdown、TXT、常见图片和普通网页。扫描件 PDF 的 OCR 延后实现。

### 5.4 Wiki 维护和复核

每次导入资料或一轮讨论结束后，Wiki 维护器可创建或修订相应的资料、主题、实体或群聊结论页。

- 原始资料永不修改。
- Wiki 更新记录来源链接、生成时间和修订原因。
- `wiki/index.md` 列出已维护页面及其简述。
- `wiki/log.md` 追加带日期和操作类型的日志。
- 变更立即写入，同时进入待复核队列。
- 用户可查看差异、接受、标记错误或回退到前一版 Markdown。

## 6. 可靠性和安全性

- 单个供应商故障只影响对应模型，其他模型仍可完成本轮。
- 仅对确认的瞬时网络错误自动重试一次；对可能已计费的生成请求不自动重试。
- 无效密钥、额度耗尽、超时、决策输出格式错误、不支持的内容和提取失败均需显示明确状态。
- 决策格式错误会记录为该模型的调度失败，不会进入回复队列。
- 用户可单独重试一个模型，或跳过它继续讨论。
- 日志会脱敏密钥；除用户主动保存为消息或资料的内容外，不额外记录提示词。
- 所有文件操作限制在用户选定的工作区目录内。

## 7. 持久化模型

SQLite 保存供应商配置元数据（不含密钥）、会话、消息和事件、资料元数据、引用、Wiki 修订元数据、复核状态和搜索元数据。

Markdown 文件是可浏览、可迁移的长期知识库成品。SQLite 只引用 Markdown 路径和修订记录，不替代人可读的 Wiki 层。

## 8. 验收标准

1. 用户可以配置并校验四家供应商中任意一家的密钥。
2. 用户可创建含至少两个模型、角色和可选资料附件的会话。
3. 用户消息会触发独立模型决策、公开理由、自然接话、全员沉默结束和 12 条上限。
4. 一个供应商失败不会终止其他模型的参与。
5. 受支持资料会保存在 `raw/`，可在对话中被引用，并生成资料记录。
6. 完成的讨论会创建或更新带引用的 Wiki 页、`index.md` 和 `log.md`，并产生待复核项。
7. 用户可以查看并回退自动写入的 Wiki 修订。
8. API Key 不会出现在 SQLite、Markdown、原始资料或应用日志中。

## 9. 验证策略

- 单元测试：决策解析、事件排序、12 条上限、冷却与点名规则、供应商故障隔离、Wiki 差异和回退。
- 适配器集成测试：使用供应商模拟响应验证请求与响应归一化。
- 端到端桌面测试：配置模型、多模型讨论、附件、Wiki 生成、复核、回退、重启持久化、无效密钥、断网、超时、全员沉默和多个模型同时希望发言。
- 人工验收：验证在模型回复、沉默、失败或被点名时，交互状态始终清晰可理解。

## 10. 交付边界

实施计划应交付上述完整工作流的薄切片。高级搜索、OCR、批量导入、定时维护、云同步、多用户能力和更丰富的图谱视图明确列为后续工作。
